# NUT-10: Spending conditions

`mandatory`

`used in: NUT-28`

---

An ordinary ecash token is a set of `Proofs` each with a unique string `secret`. To spend such a token in a [swap][03] or a [melt][05] operation, wallets include `proofs` in their request. To authorize a transaction, the mint requires that the `secret` has not been seen before. This is the most fundamental spending condition in Cashu, which ensures that a token can't be double-spent.

On [v3 keysets](02.md#keyset-id-v3) the `secret` is a public key, which authorizes the spend and can commit to further conditions. Earlier keysets use a random string, or the [well-known JSON Secret](legacy/10.md#well-known-secret).

The keyset version ([NUT-02][02]) alone selects the rules.

## Nutroot secrets (v3 keysets)

For v3 keysets, `Proof.secret` is a compressed secp256k1 public key ([NUT-00](00.md#secret-bytes)).

A proof without spending conditions uses a bare (untweaked) key. The owner holds the keypair `(k, K = k*G)`:

```
secret = K
```

A proof with spending conditions commits them into the key, following [BIP341](https://github.com/bitcoin/bips/blob/master/bip-0341.mediawiki)'s construction with Cashu tags. The secret is the tweaked key:

```
secret = P = K + t*G,  where  t = tagged_hash("Cashu_NutrootTweak", K || merkle_root)
```

`K` is the **internal key** (33-byte compressed) and `merkle_root` commits to a tree of [condition leaves](#condition-leaves). `tagged_hash` is [NUT-00](00.md#tagged-hashes)'s. The tweak `t` is reduced mod the curve order `n`.

A secret has two spend paths, as in BIP341: the **key path**, a signature by the secret's own scalar ([NUT-00](00.md#key-path)), and the **script path**, which reveals one leaf of the tree with its merkle path and satisfies that leaf ([below](#script-path)).

### The internal key

`K` takes one of three forms:

- A **single-party** key: its holder can key-path spend, and without conditions it is the secret, untweaked.
- An **aggregated** key (MuSig2, FROST: nobody holds its scalar) **MUST** carry at least the empty tweak `t = tagged_hash("Cashu_NutrootTweak", K)`, no merkle root bytes.
- A **NUMS offset** key makes the secret **script-only** (unspendable via key path): BIP341's NUMS point `H` offset by a fresh random scalar.

  ```
  H = 0250929b74c1a04954b78b4b6035e97a5e078a5a0f28ec96d547bfee9ace803ac0
  K = H + u*G          u: a fresh 32-byte random scalar per proof
  ```

  `H` **MUST** be `lift_x(SHA256(G_uncompressed))`: SHA-256 over G's **65-byte uncompressed** SEC1 encoding, taken as an x-coordinate.

  `u` **MUST** be fresh per proof and **MUST** be disclosed in [spend info](00.md#spend-info); holders verify `K - u*G == H`. Seeded wallets derive it per [NUT-13][13] type `0x02`.

### Condition leaves

A serialized leaf is:

```
leaf = leaf_version (1 byte) || leaf_type (1 byte) || field TLVs
```

The field TLVs follow [NUT-00](00.md#tlv-encoding)'s field-stream rules. That exact byte string is the leaf everywhere: in spend info, in a witness, and as the hash preimage. Leaf version `0x00` is the declarative family defined here; all other versions are reserved and **MUST** be treated as unsatisfiable.

The field vocabulary of version `0x00` (allocated types are even; odd types are reserved):

| Field  | Type   | Value                                                   |
| ------ | ------ | ------------------------------------------------------- |
| `n`    | `0x02` | signature threshold, 1 byte                             |
| `keys` | `0x04` | concatenated 33-byte compressed public keys, one record |
| `time` | `0x06` | unix seconds, minimal big-endian, at most `2^53 - 1`    |
| `hash` | `0x08` | SHA-256 digest, 32 bytes                                |

- An unknown field, odd ones included, **MUST** be rejected.
- A known field on the wrong leaf type is malformed and **MUST** be rejected.

The core leaf types, which every v3 mint and every wallet implementing this NUT understands:

| Leaf        | Type   | Fields              | Satisfied by                                                            |
| ----------- | ------ | ------------------- | ----------------------------------------------------------------------- |
| `threshold` | `0x01` | `n`, `keys`         | signatures by `n` distinct listed keys                                  |
| `after`     | `0x02` | `n`, `keys`, `time` | verifier's clock >= `time`, plus signatures by `n` distinct listed keys |
| `hashlock`  | `0x03` | `n`, `keys`, `hash` | preimage of `hash`, plus signatures by `n` distinct listed keys         |
| `commit`    | `0x04` | `hash`              | no witness: it binds the tree to 32 bytes of outside context            |

Other NUTs define further leaf types and fields, each listed in these tables with a link to its NUT; an allocated number keeps its meaning. Leaf types `0x05` and above are unallocated. An unknown leaf type **MUST** be treated as unsatisfiable, disabling only that path of that proof.

Leaf validation, enforced when building **and** when verifying a disclosed tree:

- `n` **MUST** be at least 1 and at most the number of listed keys.
- `keys` **MUST** list at least one valid compressed secp256k1 point; two keys sharing an x-coordinate are one signer counted twice and **MUST** be rejected.
- A leaf body (the bytes after `leaf_version`) **MUST NOT** exceed 512 bytes, so a serialized leaf is at most 513 bytes.
- A `commit` leaf carries `hash` and no other field. A witness revealing it **MUST** be rejected.

Multisig is a `threshold` leaf; a refund is an `after` leaf naming the refund keys; an HTLC is a `hashlock` leaf. Combinations are multiple leaves in one tree, and only the exercised leaf is ever revealed. A `commit` leaf beside them binds the proof to outside context, its `hash` defined by the protocol using it (eg a Nutzap's Nostr event).

Every spendable leaf type names at least one key.

### The tree

```
leaf_hash = tagged_hash("Cashu_NutrootLeaf", serialized_leaf)
branch    = tagged_hash("Cashu_NutrootBranch", min(h1, h2) || max(h1, h2))
```

The merkle root of a single leaf is its leaf hash. For more leaves, the fold is normative: sort the leaf hashes ascending (lexicographic byte order), then pairwise per level, an unpaired last hash promoted to the next level unchanged, until one hash remains.

Duplicate leaves are permitted; the fold **MUST NOT** deduplicate. See the [test vectors][tests] for a worked fold, including the promoted odd leaf and a duplicate pair.

A merkle path is the list of sibling hashes from the leaf to the root. A tree of more than 8 leaves **MUST** be rejected, so a path has at most 3 sibling hashes.

### Script path

```json
{
  "leaf": "<serialized leaf, hex>",
  "control": { "K": "<33-byte hex>", "path": ["<32-byte hex>", ...] },
  "signatures": ["<128-char hex>", ...],
  "preimage": "<hex>" // hashlock leaves only
}
```

The presence of `leaf` selects script-path verification. The verifier **MUST**:

1. Reject a `path` containing more than 3 sibling hashes.
2. Recompute `leaf_hash -> root` through `path`, then the tweak from `K` and the root, and check that `K + t*G` equals the secret; otherwise reject.
3. Parse the leaf, failing closed on any unknown version, type, or field.
4. Evaluate the leaf: for `after`, check its local clock is at or past `time`; for `hashlock`, check `SHA256(preimage) == hash`, with the preimage exactly 32 bytes; then count the distinct listed keys with a valid BIP-340 signature over the [input digest](00.md#the-transaction-transcript) and require at least `n`.

Thresholds count distinct satisfied keys. A witness is invalid if `signatures` holds more entries than the leaf lists keys, if any entry is not a 64-byte BIP-340 signature, or if `preimage` is present on a leaf other than `hashlock`. Mints **MAY** reject a serialized witness longer than 4096 characters; every valid witness fits when compactly encoded.

### Key uniqueness

A v3 secret is a key, so [NUT-00][00]'s unique-secret rule is met by key derivation: a seed-derived key ([NUT-13][13]), a blinded static key ([NUT-28][28]), a stored random keypair, or a fresh NUMS offset. The same `K` under different trees gives distinct secrets, but script-path spends that reveal a shared `K` link their proofs.

> [!NOTE]
> Key-path signatures verify x-only: `02 || x` and `03 || x` are distinct secrets with separate spent-state entries, yet one scalar spends both. Wallets and protocols **MUST NOT** assume an x-only key identifies one proof.

Key derivations for v3 keysets **MUST** be hardened at every step: one non-hardened BIP-32 child plus the xpub recovers the parent and every sibling.

### Spend info

A locked proof carries its tree, internal key and NUMS offset in [spend info](00.md#spend-info), verified on receive per [NUT-00](00.md#receive-time-verification).

### Signaling

Support is signaled by the keyset itself: a mint advertising a v3 keyset ([NUT-01][01], [NUT-02][02]) **MUST** implement everything in this section. The `MintMethodSetting`s of [legacy NUT-10](legacy/10.md), [NUT-11][11], [NUT-14][14] and [NUT-20][20] apply only to pre-v3 keysets.
